# 主分支安全与预期行为复查

审查版本：`aac551b`（main）。本轮仅新增审查测试和报告，未改动生产合约，未提交。

收尾时工作区另外出现了 `src/HookBase.sol` 与 `src/PulseV4Hook.sol` 的奖励水位相关改动，
非本轮审查写入，未覆盖或回退。这份报告和下列测试结果针对审查基线 `aac551b`，
不能据此认定这些并行改动已通过验证；特别是第 2 项需在新奖励实现上重新验证。

结论：普通交易和已有资金记账保护不等于整体安全。已经用真实 PoolManager、普通测试
ERC20 和公开入口复现了份额取整导致的价值转移、再平衡标记漏更新、同一区块反复领取奖励，
以及 idle 无法恢复和极端输入回退。以下分别区分代码缺陷、经济机制和已知运行限制。

## 1. 高：小份额初始化后，捐赠可放大存款取整损失

位置：`src/VaultAccounting.sol:116-120, 137`。

`newShares = floor(newLiquidity * oldShares / oldLiquidity)` 向下取整，但随后按完整的
`newLiquidity` 加仓收费。只检查 shares 非零，不能保护拿到 1 或少数份额的存款人。
此前的手续费再投资保留了老持有人的收益归属，同时也允许每个份额代表的流动性大幅增加。

本地复现：初始 tick 为 130000、spacing 为 30，首个存款人用极小资金得到 1 份额。
随后通过真实 `PoolManager.donate` 向自己的 LP 仓位捐赠匹配比例的双币。
下一位用户存款触发再投资，以约 1.9 份额对应的本金只换到 1 份额。
存款前后池价完全相同；两人退出后：

| 指标，均为代币最小单位 | token0 | token1 |
|---|---:|---:|
| 后来用户实际支付 | 712724454211312 | 252154176969163622079 |
| 后来用户净损失 | 168615413394232 | 59654303339130059244 |
| 首个存款人扣除初始存款及捐赠后的净收益 | 168615413394228 | 59654303339130059241 |

两种代币的损失比例都是约 **23.66%**。这不依赖管理员、伪造回调、外部报价或价格变化。
金额统计不包含链上 gas；条件是初始化份额很小，且首个存款人可以向其仓位捐赠。

修复方向：使实际加仓本金与最终铸造份额严格对应，退回被份额取整排除的本金；同时考虑
初始化份额精度、防止恶意抬高兑换率及用户 `minShares`。虚拟资产/虚拟份额是常见的
[防通胀攻击思路](https://docs.openzeppelin.com/contracts/5.x/erc4626#defending_with_a_virtual_offset)，
但需要适配本合约的双资产、流动性和 NFT 份额模型，不能直接套用单资产 ERC4626 公式。

复现：`test_review_donationInflationTransfersVictimValueToFirstDepositor`。

## 2. 高经济风险：自造越界可在同一区块反复领取再平衡奖励

位置：`src/RebalanceEngine.sol:45-55, 149-151`；`src/HookBase.sol:43-56`。

`rebalance` 没有时间或奖励预算限制。调用者可以在原有 LP 退出、协议收入仍留在池账上时，
添加少量自己的普通流动性与 vault 份额，交易制造越界，然后自己调用 rebalance 领取
当前协议收入的 10%。下一次小额交易又可以制造领奖条件。

本地测试的历史收入由另一位用户支付。后来者在同一 block.timestamp 连续执行 5 次，
随后退出自己的所有仓位：

| 指标 | token0 最小单位 |
|---|---:|
| 开始时已有协议收入 | 99890218385117697 |
| 结束时协议收入 | 58984175054260226 |
| 调用者扣除交易及两种仓位投入后的净收益 | 40906043330857464 |

原有协议收入减少约 **40.95%**；调用者 token1 仅损失 15 个最小单位。统计未扣 gas。
实际经济性取决于代币价值和链上 gas，但协议确实没有约束奖励相对于所做工作的价值。

这不是重新出现了可伪造成交量的入口，也不是每 60 秒的 pokeFee 路径。它符合目前
“每次成功 rebalance 支付剩余收入 10%”的字面规则，却说明该规则可被主动刷取。
需要明确是否接受这种激励结果。若不接受，应增加每池奖励预算/冷却、与可验证新增工作
或新增收入挂钩的条件，并限制单次奖励；仅保留 needsRebalance 布尔值不足以防止该路径。

复现：`test_review_keeperRewardsCanBeFarmedRepeatedlyInOneBlock`。

## 3. 中：基础币成交量为零时，价格越界不标记再平衡

位置：`src/PulseV4Hook.sol:317-334`。

判断仓位是否越界被放在 `if (volumeInBase > 0)` 内。真实 swap 可以支付另一种币并推动
价格，但基础币数量因向下取整为零。测试中 token0 delta 为 0、token1 delta 为 -3，
价格到达 tick 130080，超过仓位上界 130050；vault 仍有流动性，needsRebalance 却是 false。
keeper 调用 rebalance 直接返回，仓位未调整。

修复方向：将用户 swap 后的位置有效性检查与成交量是否为零分离。成交量只在大于零时写入；
仓位状态根据真实的新 tick 更新。

复现：`test_review_zeroBaseVolumeMoveLeavesStaleFlagFalse`。

## 4. 运行限制：全部转成 idle 后无法恢复做市

位置：`src/RebalanceEngine.sol:48, 73-76, 122-127`；`src/VaultAccounting.sol:103`。

仅有 vault 提供流动性时，价格离开窄区间后，再平衡先移除旧仓位，可能已经没有外部
流动性来换齐两种币。测试中再平衡成功返回，但 activeLiquidity 变为 0，约
1.505763685749579663 token1（18 decimals）停在 idle，needsRebalance 被清除。
之后补充真实外部流动性并调用 rebalance，仍无法恢复。新存款报 NoActiveLiquidity。

已有份额可以正常赎回，资金没有被锁死。但必须等所有旧份额退出，才能重新接收存款；
任一持有人不退出都可以令此状态长期持续。

当前 SPEC 已明确选择这种保守退出状态，因此这属于**已实现但需要接受的运行限制**，
不能把它表述成“始终自动跟随价格做市”。若产品要求自动恢复，需要设计使用既有 idle
重新建仓的入口，保留原有份额和每池预算约束，而不是靠引入新用户资金恢复。

复现：`test_review_onlyVaultLiquidityCanBecomeIdleAndCannotRecover`，包含外部流动性
恢复后再次调用，以及旧持有人成功赎回的检查。

## 5. 低：int128 最小值取绝对值溢出

位置：`src/PulseV4Hook.sol:277-278, 441-443`。

`-a` 在 int128 内计算，a 为 `-2^127` 时溢出。真实 manager 在合法但极大的交易输入下
可以返回该 delta，随后 hook 的成交量处理以 Panic(0x11) 回退。测试没有伪造 manager
回调，也没有改生产存储。此问题限于极端原始代币数量，通常可通过拆单绕过，不是直接盗币。

修复方向：先扩宽为 int256 再取负，之后转换为 uint128；协议手续费的绝对值计算也需要一致处理。

复现：`test_review_int128MinimumInputRevertsInVolumeAccounting`。

## 6. 已知待设计：交易结果保护

deposit/withdraw 仍没有 minShares、最低取回金额和 deadline，内部换币只有根据仓位范围
设置的价格界限。用户无法在入口表达自己的报价底线；不能把 amountMax 当成最低收益保护。
本轮未新增一个独立的滑点套利复现，以上份额取整损失已有直接证据，应该优先处理。

## 验证范围及解释

全量运行结果为 **112 个测试通过**（原有 105 个，加本轮 7 个），包括 **384,000 次
不变量调用**，各 fuzz 测试 1,000 轮。将奖励复现的历史收入来源明确隔离为另一位用户后，
单独复测仍得到上述相同金额。本轮审查没有修改生产合约、部署脚本或 Foundry 配置；
之后观察到的并行修改不在这些测试结果覆盖范围内。

新增 `test/integration/ReviewBehavior.t.sol` 的五个测试专门断言缺陷/风险确实发生。
这些测试显示 PASS，代表复现成功，**不代表相应行为安全**。
`test/integration/ReviewExpectedBehavior.t.sol` 则覆盖 token0/token1 作为基础币、两个方向、
精确输入/精确输出共八种组合，依据 manager 的真实 Swap 事件核对成交量、额外手续费币种、
用户 delta 和协议收入。

现有不变量主要验证资金余额、份额总和及流动性与份额的关系，没有验证个人收益公平性，
也没有验证奖励价值。Handler 的存款最小额为 1e14，且始终提供大量外部流动性；存款和
再平衡的回退会被捕获。这些约束解释了为什么旧测试未覆盖本轮发现的问题。
