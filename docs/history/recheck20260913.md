2026-09-13，针对 [原始审查](review20260913.md) 重写测试，检查重构后的工作区。六类旧问题在本次覆盖的场景中未复现；隔离副本中的七项缺陷对照全部被检出。复查期间生产合约未修改。

全量结果是 **151 项通过，0 失败、0 跳过**。环境、运行命令、不变量统计与证据路径见 [测试说明](../testing.md)。原审查记录的是旧版本缺陷，不能作为当前实现的行为说明。

## 方法

使用真实 PoolManager、普通 ERC20、真实 swap、donate 和 modifyLiquidity，并从公开的存取款与维护入口触发场景。新测试用 core 的 SqrtPriceMath 构造资金投入，不使用项目自己的份额或流动性算法来证明这些算法正确。需要报价的场景先真实执行交易，再恢复快照取得报价。

攻击前置条件必须成立：初始流动性足够小，受害者确实支付双币，测量币成交量确实为零，仓位确实越界，奖励池确实已充值且预算已生效。维护必须实际换区间并回到 Active，不能用无操作的成功调用代替。

Review 专项共 15 项，没有用 catch-and-skip 跳过失败场景；预期回退会核对错误及资金、份额、凭证是否完整回滚。

## 旧问题与当前观察

| 旧问题 | 新验证 | 当前观察 |
|---|---|---|
| 小额初始化后捐赠，转走后来者价值 | 原始 1.9 倍投入场景；1,000 组捐赠金额、投入比例、两种基础币与两种退出顺序 | 未复现原来的大额价值转移，受害者本金与攻击者收益满足舍入误差界限 |
| 同区块反复抽取历史协议收入 | 收入由另一用户产生；启用并充值奖励池；5 个地址分别制造真实越界、维护和领取 | 协议收入保持不变并可全额提取；配置 60 秒冷却时，同区块只有首次工作获得补贴 |
| 零基础币成交量导致漏判越界 | token0 基础币向上越界，token1 基础币向下越界；断言成交量确实为零 | 两个方向均识别越界，维护没有静默跳过 |
| idle 无法恢复 | 无外部流动性时进入 idle；补充外部流动性后公开恢复，或由新存款触发恢复 | 保留原份额，恢复使用原有资产，不拉取老持有人的新资金；失败存款保持原账 |
| int128.min 取绝对值溢出 | 两种基础币、收费开启和关闭；真实输入为 2^127，检查钱包 delta 和成交量 | 极值交换通过分次结算成功，没有取负溢出 |
| 缺少存取款结果保护 | 先取得真实报价，再捐赠增加老份额价值或交易改变提款组成 | minShares 与最低提款金额拒绝过期报价，资金和凭证完整回滚 |

捐赠场景保持价格不变，误差界限取 core 对 **1 个流动性单位**的双币成本，再加 3 个原始代币单位，没有按存款金额的百分比放宽。

极值输入使用 [测试专用分次结算路由器](../../test/utils/SplitSettlementRouter.sol)：core 的单次正向结算受 int128 范围约束，需要拆分还款，才能验证真实的 2^127 输入。这个结果不代表任意外部路由器都支持相同极值。

此外，八种基础币、交易方向、精确输入或输出的组合，同时核对对应池的 Swap 事件、实际钱包变化、收费币种、协议收入和成交量，防止通过只检查内部计数掩盖结算错误。

## 缺陷对照结果

为了确认测试能区分修复前后的行为，在临时副本中逐项引入以下缺陷。未修改的隔离副本先通过全部 15 项 Review 测试；七项对照随后均出现目标测试的预期失败。

| 对照名 | 引入的缺陷 | 实际检出 |
|---|---|---|
| donation_rounding | 恢复低精度初始份额、按候选流动性全额收费，撤掉舍入保护 | 攻击者获得受害者 token0，资金公平性断言失败 |
| treasury_rewards | 每次维护从历史协议收入支付 10% | 维护后协议收入减少 |
| sybil_cooldown | 撤掉已付奖励的冷却判断 | 第二个地址在同区块再次获得奖励 |
| range_detection | 禁用越界状态识别 | 零基础币成交量时错误判断无需维护 |
| idle_recovery | 不把 idle 作为需要恢复的状态 | idle 可恢复性断言失败 |
| signed_minimum | 在 int128 中直接取负 | 极值交换返回封装了 Panic(0x11) 的 core 错误 |
| minimum_shares | 撤掉 minShares 检查 | 过期报价存款没有按预期回退 |

恢复旧份额算法的副本再次产生攻击者 token0 净收益 **168615413394228 个原始单位**，与原审查吻合；修复版的同一场景通过。

这些副本保留新版 ABI，并逐项恢复旧机制或移除保护。不能把结果表述为“新版测试直接在旧提交上运行”。脚本只认可目标测试的预期失败，编译、初始化或测试选择错误不算检出。

## 仍然允许自造维护需求领取补贴

测试明确观察到：第一个制造有效换区间工作的地址可以获得 1 个测试奖励币。这是当前奖励规则允许的行为，见 奖励说明(奖励池文档,已随 keeper 移除)。

在本组测试的 60 秒冷却下，换地址不能绕过每池冷却，跨 UTC 午夜也不会清除冷却；第二个池不能绕过全局预算。预算在奖励记账时消耗，领取不会恢复预算。配置 `minInterval = 0` 则没有冷却保护，不能推广本测试的“同区块只付一次”结论。

本次验证表明历史协议收入不会被维护奖励抽走，且配置的补贴预算和冷却生效。它没有给奖励币或制造越界的成本定价，因此不能证明人为制造维护需求一定无利可图。
