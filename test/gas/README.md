# Gas 测量

本目录测量固定场景中实际调用的 gas，测试代码见 [VolumeGas.t.sol](VolumeGas.t.sol)。费用模型与模块职责分别见 [SPEC](../../SPEC.md) 和 [架构说明](../../docs/refactor.md)。

## 当前结果

本地验证使用 Foundry v1.5.1、Solidity 0.8.26、Cancun、via IR 和 optimizer 200 runs,完整环境见 [测试说明](../../docs/testing.md)。数值来自测试输出的 `swap execution gas` 或 `fee query gas`,不是 Forge 显示的整项测试总 gas。

| 场景 | 含金库的旧版本 | 当前版本 |
|---|---:|---:|
| 首次交换,成交量状态为空 | 261,386 | **247,495** |
| 同 tick、同一小时交换 | 168,167 | **162,079** |
| 同 tick、下一小时交换并刷新费率 | 193,811 | **163,159** |
| 一小时后查询费率 | 40,120 | **39,522** |

左列是移除金库前的记录。当前版本的 `afterSwap` 不再读写金库仓位状态,也不再判断越界,
因此每笔交换都更便宜;"下一小时刷新"一项降幅最大(约 30k),因为费率刷新不再走独立的
带冷却检查的路径,而是并入每区块首笔交换。

### 协议费:mint 与 take 的对比

以下对比保留改用 claim 时的测量,当时中心权重为 2、测试 MIN_FEE 为 500。

协议费改为铸造 ERC-6909 claim 而不是 `take` 真实代币,在这里用的简单测试代币上每笔交换省约 **446 gas**:

| 场景 | `take` | `mint` |
|---|---:|---:|
| 首次交换 | 247,941 | 247,495 |
| 同 tick、同一小时交换 | 162,525 | 162,079 |

真实代币(带黑名单检查、转账回调或转账税)的 `transfer` 更贵,差距会更大,但**这个改动的理由不是 gas**——
是为了让交换路径上不出现任何代币外部调用,见[架构说明](../../docs/refactor.md#为什么用-erc-6909-claim-而不是-take)。

这个表只覆盖交换和费率查询两条路径,不含协议收入提取(提取会打开 manager 锁并分块 burn/take)。

## 测量方法

[公共 fixture](../utils/PulseV4HookFixture.sol) 使用真实 PoolManager、路由器、Hook 和测试代币；本目录在 setUp 中存入两币各 `1e21` 的最大预算，tick spacing 为 30，交换输入为 `1e14`。初始测量时间设为 100 小时又 15 分钟。默认测试 LP 费率范围为 100–3,000 pips，C 为 300，成交量每小时衰减为一半。

对于“已有成交量”场景，前一次交易也在 setUp 中完成。这样被测调用从新的测试交易开始，不会把同一交易内反复写入已访问槽位的成本当成多笔独立交易的成本。

计量使用调用前后的 `gasleft()` 差值。交换覆盖真实 router → manager → hook → token 路径；查询覆盖 `computeFee` 调用。两者都不包括交易固有 gas、rollup 数据费用、部署及准备过程。币种实现、价格路径、流动性和缓存状态变化都会影响结果。

在仓库根目录复现：

```sh
forge test --match-path 'test/gas/VolumeGas.t.sol' -vv
```

## 历史成交量模型对比

以下保留此前对基线 `60df9aa` 的测量：在基线上加入同一测量 fixture，并将继承的 setUp 改为 virtual 后运行。它记录的是旧成交量模型迁移到点成交量模型的效果，不是本轮重构新增的全部收益。

| 场景 | 旧模型 | 点成交量模型的历史记录 | 降幅 |
|---|---:|---:|---:|
| 首次交换，成交量状态为空 | 947,322 | 262,818 | 72.3% |
| 同 tick、同一小时交换 | 296,785 | 169,335 | 42.9% |
| 同 tick、下一小时交换并刷新过期费率 | 366,823 | 195,169 | 46.8% |
| 一小时后查询费率 | 54,885 | 39,971 | 27.2% |

历史比较使用 Solidity 0.8.26、optimizer 200 runs、via IR 和本地 Foundry EVM。旧版本结果没有在这次文档整理中重新执行。

## 为什么使用点成交量

点成交量实现每笔交换只写全局桶和交易结束 tick 的桶；每个桶的数量与小时锚点装在一个槽位里。此前模型会把成交量复制到 15 个相邻 tick，连同全局记录涉及 32 个槽位；点模型将这部分写入缩到 2 个槽位。

计算费用时读取附近五个 tick 桶，中心权重为 3，并读取全局桶。模型改变了成交量的空间分布含义，不能仅因为保留了费用常量，就认为两个版本会产生完全一致的费率信号。

普通前缀数组需要在旧 tick 发生新交易后更新后缀；差分数组把成本转到查询；Fenwick 树能限制复杂度，但增加每笔交换的存储写入，也需要处理惰性衰减。当前查询窗口固定为五个桶，因此使用直接点写入和短循环。仓库没有实现 Fenwick 版本，也没有相应实测比较。
